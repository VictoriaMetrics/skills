# Preset workflow guide v1

Use this workflow to discover signals and build presets in MCP clients, including AI Copilot. Complete a preset by generating config and alert files or identifying blocking inputs. Editor changes or offers to generate later are not completion.

## Scope and budgets

Reuse the user's authorized datasource, tenant and service scope. An explicitly selected multitenant route is allowed; never enumerate tenants or broaden scope automatically. Discover the available tools and their schemas. Missing capabilities are limitations, not empty data. Keep existing user constraints; do not silently change cadence, topology, workload size or history to make sizing succeed.

Initial workflow budget: at most 10 metadata calls, 100 items per call, one day of metadata, and five candidate queries profiled. Narrow after broad discovery. Profile with explicit per-query `limit: 5`, `verbose: false` and fixed start/end/step; report samples. Count repeat profiling toward the five-call budget; reuse results. Bound points by window/step too. Copilot may enforce request budgets; elsewhere these are instructions, not TSDB scan-cost guarantees. Stop on overload/timeouts rather than retrying automatically.

## Discover and evaluate

1. Use vmanomaly_discover_metrics with metric_names, then label_names/label_values and bounded series inspection as needed. Metric prefixes are hints, not evidence of semantics. Preserve completeness and warnings; small returned lists do not prove exact fleet cardinality.
2. Choose a small actionable signal set. For node-exporter, investigate CPU activity, available-memory ratios, filesystem capacity and disk/network rates only if the required metrics and labels exist. Convert counters to rates. Validate units and filesystem/device exclusions from observed data. Preserve host identity unless the user deliberately chooses service aggregation; explain that aggregation can hide failing hosts.
3. Execute candidate expressions and inspect their samples/history using query and timeseries-characteristics tools. List installed models and retrieve relevant model schemas. Prefer online MAD, z-score, quantile or envelope models when appropriate. Use multivariate models for aligned related signals and peer models for comparable complete peer groups, not merely because multiple metrics exist. Classify deterministic checks separately; do not invent an ML workload for static conditions.
4. Choose guardrails from user intent and observed data; disclose tentative choices. Schema-valid is not evidence of fit quality. Apply the quality check below before file generation; use each task's declared model/schema. Inference ordinarily starts at 5m; choose query sampling separately to preserve relevant events. Preserve explicit user cadence and explain tradeoffs if it is too coarse.

For model choice, consult the [model-selection guide](https://docs.victoriametrics.com/anomaly-detection/guides/model-selection/). The page is linked, not copied into this workflow. Use `vmanomaly_search_docs` for related installed documentation and `vmanomaly_read_doc_section` with returned URI/offsets; do not assume this linked page is bundled or fetch it without available browsing. Live model schemas take precedence over static examples.

Favor `quantile_online` for negligible-trend data with repeatable uneven/plateau phases that benefit from explicit seasonal buckets, especially custom cycles such as `seasonal_interval: 14d` and `min_subseason: 3h` (112 buckets per series). Uneven describes recurring phase shape, not irregular sampling. Check repeated-cycle evidence and observations per bucket. For other non-trivial temporal profiles prefer Temporal Envelope; retain MAD/z-score for simple stationary signals. Envelope may need less state and fit/infer faster than fine-bucket quantile models, but verify workload-specific sizing/timing rather than promising savings. Do not substitute weekly DOW for a 14-day cycle or assume envelope supports arbitrary periods. Preserve user choices and models with demonstrated quality advantages.

## Quality check before files

Inspect fit/evaluation coverage, gaps and level changes. Digest decay advances on updates, not elapsed missing time. Explain proposed window changes; never bridge long gaps or discard incidents to improve a score.

Run bounded autotune unless declined, already evaluated, or unsupported; disclose skips. Assume `anomaly_percentage: 0.02` (1–2% anomalous points), not a false-positive guarantee or quota. Preserve query policies. Use two sequential studies; disclose untuned groups: `limit: 5`, `optimization_params: {n_trials: 32, timeout: 8, exact: true, n_jobs: 1}` for online models. Prefer supported `replay` with production `fit_window`, `fit_every`, `infer_every`, start/end and step; verify returned replay metadata. Replay overrides fold settings and requires preceding fit history. Otherwise use regular folds and disclose cadence mismatch. Never bypass missing history with leaky one-fold in-sample scoring.

Use `vmanomaly_create_autotune_task`; poll `vmanomaly_get_autotune_task` sequentially; prefer supported `wait_seconds: 10`, else wait 2–5s. Stop at 10 polls and retain the task ID; never recreate running/failed tasks or use unfinished results.

Compare tuned and untuned candidates on later observations excluded from tuning, using replay or separate detection tasks (`exact` alone does not match schedules). Check baseline, per-series/aggregate anomaly fractions and streaks; keep joint/peer groups intact. Revisit history/model choice before widening thresholds; do not hide sustained changes to meet a target. Keep simpler candidates when tuning adds no benefit. Report quality limitations; carry selected parameters into one complete bundle.

## Size and assemble

Estimate resources for the proposed topology, actual or explicitly estimated output-series counts, sampling, inference cadence and history. A metadata sample count is a lower bound, not fleet size. Explain assumptions, preserve headroom, and do not extrapolate a small estimate into a claim that memory will barely grow with fleet size.

Assemble a complete config with reader, production writer, named models, query mappings and schedulers. Set an explicit non-null `fit_every` for every active periodic scheduler: omission inherits `infer_every` and can repeatedly refit the entire history. For continuously updating online models, choose a deliberate long interval (for example `1000w` when periodic rebuilding is not intended); this is not a true fit-once mode and startup/restore behavior still applies. Batch models need a suitable regular refit interval. Use separate schedulers when their refit needs differ, and use the same intervals in resource estimates. Prefer supported short class aliases (`vm`, `periodic`, `mad_online`) and omit unneeded defaults; retain intentional zero/false/null values and user-defined model/query/scheduler names. Preserve explicit aliases and per-query policies. Reuse configured destinations only when their intended role is known: the reader URL is not automatically the score-writer URL. Use secret references, never invented credentials.

With a long refit interval such as `1000w`, explicitly choose how the online model forgets old data. For online MAD, z-score and quantile models, prefer `0 < decay < 1` when adaptation to drift is intended; `decay: 1` retains historical weight and can become slow to adapt. Keep 1 only for a deliberate cumulative baseline and explain that choice. Select decay from the desired adaptation horizon and the model's update semantics, not from `fit_every`. Do not assume one decay step per inference job: z-score weights individual samples, while digest-based models can apply decay per update batch; seasonal buckets update only when their phase receives observations. Check the installed schema and documented update behavior before translating decay into wall-clock time; disclose uncertainty rather than inventing a precise horizon. Stronger forgetting adapts faster but may learn sustained anomalies as normal. Check warmup and `history_strength` together with decay; stronger initial history is not a substitute for forgetting. For peer models, check the effective-sample warmup limit at the chosen decay. For rolling or temporal-envelope models, use their schema-supported history/window controls instead of injecting a generic `decay` field. Validate all proposed parameters and preserve explicit user choices.

For recommendation/preset requests, an unknown writer must not block draft generation. Use `http://replace-me.invalid:8428` as the writer URL and pass `required_inputs: ["writer.datasource_url", "writer.tenant_id"]` when both destination and tenant/topology are unknown. Do not copy the reader tenant; omit the writer tenant until known, or preserve an explicitly supplied writer tenant and mark only the URL missing. Never probe or write to placeholder destinations. If only the writer tenant/topology is unresolved, mark only `writer.tenant_id`. Explain that cluster writer routing must be configured for the actual destination. Ask first instead when the user explicitly requests deployment-ready output. A noop writer cannot produce alert artifacts. Missing incident URL can be omitted with a warning; it need not block files.

The artifact response contains `required_inputs` entries with `field` and `instruction`, and `deployment_ready: false`. The renderer includes draft comments in both YAML files and the UI labels the cards Draft when required inputs remain. State these substitutions in chat. Even an empty checklist does not prove deployment readiness: connectivity, sizing and delivery remain unverified. If a server rejects the new draft fields, do not silently drop them or claim complete files; report the missing capability.

## Produce files and finish

Call vmanomaly_generate_preset_artifacts with the complete config and alert policy. It validates the full configuration and returns config_yaml, alerts_yaml, validation and warnings. Preserve the complete returned `config_yaml` and `alerts_yaml`, including comments and draft requirements. Do not edit or reconstruct individual sections after validation. If settings change, regenerate the complete matching artifact pair and revalidate; never mix files from different generations. Use full-config validation separately only when useful for diagnosing an intermediate config. Fix correctable schema failures without changing the user's constraints; report unresolved errors honestly.

Choose alert evaluation and persistence independently of sampling. A for-duration measures how long the alert expression remains true across alert evaluations; it never guarantees a count of independent model observations, even when divided by the inference interval. Do not describe 15m persistence as three observations or evaluations. Model min_consecutive_points is a separate control; stale/repeated scores require freshness handling. Retain source identity and incident-link annotations. Schema validity does not check connectivity, history, fit quality, score freshness, alert delivery or startup.

In a Copilot UI with artifact cards, successful tool results become downloadable vmanomaly.yaml and alerts.yaml files. Do not reproduce the files through display_yaml just to enable downloads, and do not invent download URLs. Other clients can save the returned strings. State which files were generated and summarize warnings and unresolved validation. Do not stop at “I can generate rules next.”

Query-editor suggestions are optional previews, not a prerequisite for building files. Do not mutate the workspace unless the user requests that preview. If suggestions are requested, use the current revision and do not resubmit unchanged settings or claim changes unsupported by the tool result.

Use the deployment adapter below for manifests; dashboard JSON needs separate assets. File generation does not authorize deployment or alert delivery.

For a requested Kubernetes deployment, consult the [anomaly Helm chart](https://github.com/VictoriaMetrics/helm-charts/tree/master/charts/victoria-metrics-anomaly) and [VMAnomaly Operator resource guide](https://docs.victoriametrics.com/operator/resources/vmanomaly/). Choose a release compatible with the installation and inspect pinned chart values/schema or CRDs before rendering; Chart.yaml alone describes a chart, not all supported deployment settings. Fetch assets only from an authorized source at a pinned revision, record provenance/checksums, and validate a complete staged bundle before publishing it locally. Preserve previous bundles on failure and never patch an existing deployment in place as part of file generation.

## Deployment and state choices

First inspect the live artifact tool schema: use `deployment` only if explicitly supported. Otherwise generate the base pair and use a separate supported deployment adapter with its validated spec, or report deployment files unsupported. The bundled `scripts/render_bundle.py` does not implement storage selection or volume wiring. The following unified flow requires that capability.

Check deployment/storage preferences already supplied in the conversation. If both are known, finish selection and sizing first, then call the artifact tool once with the complete config and `deployment`; return the base YAML and selected deployment files together. Do not emit a preliminary base-only bundle or use artifact generation as an intermediate validation step. Use supported draft placeholders for missing writer, license or volume details.

Only when deployment or storage preferences are genuinely missing, generate base vmanomaly.yaml and alerts.yaml without `deployment`, then ask one compact question for the missing choices: Docker Compose, Helm or VM Operator; persistent state (recommended when durable storage exists) or ephemeral RAM? Keep those base cards available while awaiting the answer. Reuse known choices; generate all alternatives only on request.

When the missing choice arrives, regenerate the complete matching bundle with `deployment`: `targets` (compose/helm/operator), `storage` (persistent/memory), and an explicit released `image` tag. Regenerate only for changed inputs or a failed generation. Use the tool schema for supported chart/Operator versions and optional namespace, license Secret, volume size, StorageClass and resource requests/limits. Never guess installed storage classes or licenses. Treat unknown storage size as a required input, not a capacity recommendation. Follow the adapter’s version and storage restrictions; never silently switch modes or drop unsupported connection fields.

Persistent mode pairs `settings.restore_state: true` with model/data directories and volume wiring. RAM mode pairs `restore_state: false` with no disk-mode environment variables. Align the new config with the user's chosen mode; preserve existing explicit preferences or clarify conflicts. Disk mode alone does not guarantee restart durability. Size for I/O, restart warmup, state and temporary fit data. Deployment files remain drafts pending secrets, storage and live checks. The tool returns a coherent replacement `files` list with per-file requirements, validation and provenance; preserve it intact, including base YAML. Helm output is values.yaml plus pinned-chart instructions, not a fabricated Chart.yaml or a complete chart archive. Operator output is a CR; alerts still need installation in vmalert. Never claim deployment or live validation.

For new continuously updating online presets, recommend `settings.retention: {ttl: 1w, check_interval: 5m}` unless the user specifies another policy. TTL is otherwise disabled by default. Keep `check_interval` below `ttl` and every scheduler’s `fit_every`; reduce 5m for refits at 5m or less. Preserve deliberate overrides. TTL evicts stale model instances, while decay forgets old observations within active models. One week is not a RAM/disk cap; include churn-retained models in estimates and discuss shorter TTL for high churn, longer TTL for intermittent entities, cold starts after eviction, inference/refit constraints, and multivariate/peer group retention. Override model/scheduler TTLs for differing lifetimes. Do not claim model TTL cleans every file on the volume.
